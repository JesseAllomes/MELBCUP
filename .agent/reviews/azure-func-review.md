## Diff of tools/live_collector.py (repo 293 lines vs package 336)
Purely additive: `Collector.snapshot()` and `Collector.restore()` (PKG:173-214), no existing line changed, so GitHub-run behaviour is unaffected. Restore tolerates bad state and cold-starts. The issues are in how state is used (D1, D3, D4, D10), not the diff itself. The change is NOT in the repo (the repo copy lacks it), so code in Azure and code in git have already diverged (D11).

## Defects
1. BLOCKER. Cross-invocation dedupe breaks the data consumers. `last` (the same_as map) is persisted in state (PKG:175-190, restore ~205-212), so almost every first record of each per-minute "run" is a `same_as` marker whose payload lives in an earlier run/file. live_validate.py:80-94 and :128-135 resolve markers per run (key starts with `r["run"]`) and live_gaps keys by run. Failure: every market and field marker has no `data`, so "market_without_start", T-30 snapshot selection and field-meaning stats are all wrong or empty for Azure data. The prospective-evaluation purpose is defeated. Original code deduped within one run only. Fix: reset `last` at the start of each invocation (self-contained files), or at least each hour, or teach the validators to resolve same_as across runs by (what, target, obs_utc).
2. BLOCKER. functionTimeout is 20 s (host.json:3) but every HTTP request has a 30 s timeout (PKG gql), meetings refresh is 8 sequential calls (every 15th cycle), and one cycle also does schedule, market and field fan-out. Any slow cycle gets killed: the host aborts before upload (FA:86-93) and state save (FA:95), the cycle's observations are lost, and nothing is logged inside the file. On Cup day with many watched races this is likely. Fix: raise functionTimeout (e.g. 00:00:55 or more) and cut gql timeout to about 10 s for Azure.
3. BLOCKER (policy/data). cadence_divisor (CR:31-39, used CR:58-70) silently runs every 2nd or 4th minute when the mean of the last 60 durations exceeds 4 s or 8 s. Busy national racing days (Cup week) are exactly when cycles are slow, so the collector thins itself on the day that matters. live_gaps.py (--gap default 150 s) then reports outages. This contradicts the collector's "a missing cycle is an outage" principle and the 20-min/60 s cadence it replaces. Durations never update on skipped runs, so recovery is slow. Decide cost vs completeness explicitly. Quick estimate: 1440 invocations/day x about 5 s x 2 GB (if the default 2048 MB instance size is used, unverified) is about 14k GB-s/day, so about 115k GB-s over the 8-day window, over the 100k GB-s monthly free grant. Fix: set the instance to 512 MB (cuts GB-s about 4x) and remove the divisor, or make it opt-in via a setting.
4. SHOULD-FIX. State advanced before upload succeeds. `run_once` sets `self.collector_state` and `invocations` in memory (CR:105) and the module-global `session` (FA:33,47) is reused. If a blob upload raises (FA:89-93) or the process dies after an in-memory update but before save_state, the cached `session` keeps the new `last` map while the blob file is lost. Later markers then point at payloads that were never stored (permanent loss). Fix: on any exception in `collect`, set `session = None` so state reloads from the blob; or only commit memory state after upload succeeds.
5. SHOULD-FIX. publish is not idempotent and can overwrite `live` data. The path is derived only from the hour (FA:118). commit_github_file replaces the file at that path (CR:158-166). If the function dies (20 s timeout) after the commit but part-way through the delete loop (FA:122-123), the next run rebuilds the same path from the REMAINING blobs and replaces the full file with a subset. The same happens if a late blob (cycle delayed past hh:07, retry) lands in an already published hour. `live` is meant to be append-only (live_validate --git flags any non-add change; the GCS mirror's `--no-clobber` keeps the stale copy and its verify step fails). Fix: GET the path first and skip or use a unique name (e.g. include the first blob name or a count), delete blobs only after the commit is confirmed, and give publish a longer timeout. Also, a backlog after an outage (many hours x about 5 GitHub calls each) will exceed 20 s.
6. SHOULD-FIX. Webhook replay marker is written BEFORE the job starts (FA:147-150). If ARM auth, GET or start fails (no role on the job, container not named "worker" -> StopIteration at FA:163, HTTP 4xx/5xx; all uncaught -> 500), GitHub's Redeliver returns "already queued" and the owner's request is silently lost. Fix: write the marker after the start call succeeds (or delete it on failure) and catch/log errors to return 502 with a clear reason.
7. SHOULD-FIX. No serialisation. reenter.yml used `concurrency: reenter` (queue, no cancel). The webhook starts a new job execution per issue immediately, so two issues opened close together run two jobs in parallel against the same data/entries log and git push, with risk of conflicts and duplicate real-world competition entries. Fix: list running executions of the job (ARM `.../executions`) and refuse or defer, or set the job to a single-execution pattern.
8. SHOULD-FIX. Cutover double-run: both reenter.yml and the webhook would fire on the same issue, entering competitions twice. Likewise live-collector.yml and the Azure collector would both write to `live` (extra load, dual runs, and the Azure commit retries fight the git pushes). Disable the GitHub workflow in the same change that turns the Azure side on.
9. MINOR. Webhook timing and robustness: GitHub waits 10 s for a response, but a cold Flex start plus MI token plus two ARM calls (timeouts 60 s, FA:161,181) can exceed that or the 20 s host limit (the delivery shows "failed" although the job may have started). It also never checks `X-GitHub-Event == "issues"` (FA:129-142, harmless today because action=="opened" plus `issue` only appear on issues events). `hmac.compare_digest` on str raises TypeError for a non-ASCII signature header (CR:187, returns 500 not 401). Fix: compare bytes, check the event header, respond fast and do the ARM work after, or accept the failed-delivery cosmetics. Also the ARM start posts the whole `properties.template`; the start API takes only containers/initContainers, so a template with `volumes` or similar may be rejected (unverified, test with a dry run). Resulting job comments/closes the issue/commits are in the job image, which is not in either repo, so parity of those steps cannot be confirmed here.
10. SHOULD-FIX. State size grows without bound: `last` keys embed the full query text per race (PKG snapshot), is never pruned, and is rewritten every minute (FA:95). Across about 8 days of all-state racing this can reach several MB uploaded 1440x/day, slowing cycles toward the 20 s limit (see D2). Fix: key by short hash of the query and prune keys for races no longer watched.
11. SHOULD-FIX. The deployed code is not in any repository (azure-inventory.md finding 2) and tools/live_collector.py now differs from main. A collector fix pushed to main will not reach Azure and vice versa. Commit function_app.py, collector_runtime.py, host.json, requirements.txt and the collector change to the repo (and add a deploy workflow).
12. SHOULD-FIX. Provenance: the Azure `start` record (CR:75-83) omits `version` (sha256 of the collector) and `cadence` that the original writes (live_collector.py main, lines ~148-150). live_gaps prints version `?`. Fix: add them.
13. MINOR. `corrupt state.json` is not handled: `json.loads` error at FA:50-52 is outside the ResourceNotFoundError handler, so a damaged blob fails every minute forever with no recovery. Catch ValueError and cold start.
14. MINOR. Run ids/day folder: `run` timestamp and the file date folder come from two `now()` calls (CR:72, live_collector Log._write). Around 23:59:59.9 UTC the file lands in the next day's folder under a run id of the previous day; publish then holds it a day (FA:111). Rare, not data loss.
15. MINOR. Likely cause of the host 503 to verify first: `tools/live_collector.py` does `ZoneInfo("Australia/Melbourne")` at import time and requirements.txt has no `tzdata`; if the Flex image lacks system tzdata the whole app fails indexing. Other candidates: managed identity missing Storage Blob Data Owner / Queue / Table roles needed by AzureWebJobsStorage__credential, or the extension bundle. Check App Insights / log stream. Add `tzdata` to requirements.txt regardless.
16. MINOR. publish reads GITHUB_TOKEN with `os.environ[...]` (FA:113) even when nothing is pending or the collector is disabled, so a missing token gives a KeyError every hour. Move it inside the loop. No alerting exists for publish failure (blobs just accumulate).

## Webhook verdict (specific checks)
- HMAC-SHA256 over raw body, `sha256=` prefix, constant-time compare: correct (CR:185-187); verified before JSON parse. OK.
- Replay protection: delivery-id blob with overwrite=False: works, but timing is wrong (D6). No expiry cleanup (trivial growth).
- Owner-only: `issue.user.login == repository.owner.login`, repo pinned to jesseallomes/lotto-project (lowercased), title prefix case-insensitive like Actions' startsWith, action must be "opened": parity with reenter.yml.
- What is passed to the job: only ISSUE_TITLE (full title) and ISSUE_NUMBER overrides on container "worker"; same inputs as the workflow's env. Existing secretRef env entries are re-sent as references, not values. OK.

## Minimum fixes before turning on (COLLECTOR_DISABLED=0 / webhook live)
1. Resolve the 503 (D15), then verify managed-identity roles and GITHUB_TOKEN scope.
2. D1: make dedupe per-invocation (or fix validators) and run live_validate.py on a sample of Azure output.
3. D2/D3: functionTimeout >= 55 s, shorter request timeout, drop or make explicit the cadence throttle; set instance memory to a small value and accept the cost.
4. D4: reset cached `session` on any exception.
5. D5: publish idempotent (check existing path, delete only after commit).
6. D6/D7: replay marker after success, execution-concurrency guard; D8: disable live-collector.yml and reenter.yml at cutover (keep archive-to-gcs.yml enabled).
7. D11/D12: commit the code to the repo and restore `version`/`cadence` in start records.
8. Dry run: set COLLECTOR_DISABLED=0 for a short test, run live_validate.py/live_gaps.py on the first hour on `live`, then test the webhook with a real owner-opened "reenter: <ids>" issue on a stub or dry-run job.
